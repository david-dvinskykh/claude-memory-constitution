# Installing the memory structure in Notion — instructions for the agent

You are installing the `notion-memory-constitution` template into the user's
Notion. Read this file in full and carry it out step by step. Do not walk the
user through the steps in advance — do the work and report at the end.

This file is in English so that it serves every supported language. The
structure you create is NOT in English by default: its language is chosen by
the user in step 1, and everything you create — base names, field names,
option values, the constitution, the service pages — is created in that
language. Talk to the user in that language too, from step 2 onward.

THE BASE ADDRESS of the template (BASE below) is the directory you fetched
this file from. The other files sit next to it: BASE/schema.json,
BASE/constitution.<lang>.txt, BASE/update.txt, BASE/migrations.json, and
version.json one level up: BASE/../version.json.

## Rules of execution

1. Delete nothing. No step of this installation contains a delete operation.
2. On an error, do not stay silent: say in one line what failed, then carry on
   with whatever does not depend on it. List the unfinished items at the end.
3. Write "created" only after a successful tool response.
4. Do not invent fields or options that are not in schema.json.
5. If the user already has some of this, see step 2 — do not create it twice.

## Step 0. Tools and preflight

Load the Notion tools: search, fetch, create-pages, update-page,
create-database, update-data-source, query-data-sources. The tools are
deferred; without loading them nothing will work.

Fetch BASE/schema.json and BASE/../version.json. If schema.json cannot be read,
stop and say so: the installation is impossible without it.

## Step 1. Language

Ask the user which language the structure should be in. Offer exactly the
languages listed in `languages` in schema.json, named as in `language_names`:

- `ru` — Русский
- `uk` — Українська
- `en` — English

Ask in all three, in one short line, so that the question is legible to
whoever is reading. If the user answers in a language that is on the list,
take that as the answer. If they decline to choose, use `default_language`
from schema.json.

Remember the choice as LANG. From here on, every value you take from
schema.json is taken from its `LANG` branch, and you speak to the user in
that language.

The choice is made once, at installation. Reinstalling in a different
language creates a second, separate structure — say so if the user asks.

## Step 2. Have we already installed?

`notion-search` for the template updates page, using the title from
`pages[key=updates].title[LANG]` and also its English form. If a page is found
whose body contains the line `Template: notion-memory-constitution`, the
template is already installed. In that case do not install again: carry out
BASE/update.txt instead and tell the user in one line.

## Step 3. Where to put it

Ask the user one thing and only one: which Notion page the knowledge base
should be created under. Offer a default — a separate top-level page in their
private space. If the answer is "default", create a top-level page
(create-pages with no parent).

## Step 4. Container pages

Using `notion-create-pages`, create:

1. The page `pages[key=root].title[LANG]`, icon from `icon` if present,
   in the chosen location, with `pages[key=root].body[LANG]` as its body.
   Remember its page_id as PAGE_ROOT.
2. The subpage `pages[key=cardfile].title[LANG]`, parent = PAGE_ROOT, body
   `pages[key=cardfile].body[LANG]`. Remember its page_id as PAGE_CARDFILE.

## Step 5. Databases

For every entry of the `databases` array in schema.json, in the order given,
call `notion-create-database`:

- `parent` = { "page_id": PAGE_ROOT } when `parent` is "root",
  or { "page_id": PAGE_CARDFILE } when `parent` is "cardfile";
- `title` = `title[LANG]`;
- `schema` = `ddl[LANG]`, unchanged;
- `description` = `purpose[LANG]`.

Take the data_source_id from the response (in the
`<data-source url="collection://...">` tag) and record it in a KEY → DS_ID
table. You need that table for the rest of the installation; do not lose it
and do not confuse data_source_id with database_id.

Create all 16 databases before going further: the relations reference each
other.

## Step 6. Relations

For every entry of `relations`: take the DS_ID of the base named in `on`, take
`statements[LANG]`, substitute real ids for the `[ID:key]` placeholders using
the table from step 5, and call `notion-update-data-source` with that
data_source_id.

The statements of one entry may be passed as a single string separated by `;`.

Every statement with `DUAL` creates **both** sides of the relation: the forward
field here and the reverse field in the target base. Do not add the reverse
fields separately — you would get duplicates. The same holds for
self-relations inside one base.

## Step 7. Formulas and rollups

Carry out the `computed` array the same way, taking `statements[LANG]`. Partial
failure is acceptable here: if a formula or a rollup is not created, do not
stop the installation — put it on the list of unfinished items so the user can
add it by hand. Everything else works without them.

## Step 8. The constitution

1. Fetch BASE/ + `pages[key=constitution].content_url[LANG]`.
2. Replace the placeholders in the text:
   - `[ID:facts]`, `[ID:prefs]`, `[ID:people]`, `[ID:orgs]`, `[ID:places]`,
     `[ID:things]`, `[ID:projects]`, `[ID:processes]`, `[ID:ideas]`,
     `[ID:journal]`, `[ID:docs]`, `[ID:cases]`, `[ID:bio]`, `[ID:powers]`,
     `[ID:queue]`, `[ID:inbox]` — with the data_source_id of the matching
     base;
   - `[ID:page:root]` with PAGE_ROOT, `[ID:page:cardfile]` with PAGE_CARDFILE.
     Leave `[ID:page:index]`, `[ID:page:owner]`, `[ID:page:updates]`,
     `[ID:page:history]` and `[ID:page:constitution]` as they are — you
     substitute them in step 10, once those pages exist.
   After step 10 no `[ID:` placeholder may remain in the text. If any remains,
   say so: a constitution with holes does not work.
3. Create the page `pages[key=constitution].title[LANG]`, parent = PAGE_ROOT,
   body = the resulting text. Remember its page_id as PAGE_CONSTITUTION.
4. Create the subpage `pages[key=history].title[LANG]`, parent =
   PAGE_CONSTITUTION, body `pages[key=history].body[LANG]` followed by a table
   with the columns Date · Version · What changed · Why (in LANG) and one
   first row: today's date · 1.0 · "installed notion-memory-constitution
   version <version from version.json>" · "installation". Remember
   PAGE_HISTORY.

## Step 9. Service pages

Create under PAGE_ROOT, each titled and bodied from schema.json in LANG:

1. `pages[key=owner]` → remember PAGE_OWNER.
2. `pages[key=index]` → below the body, a table of all 16 databases:
   `title[LANG]` · `purpose[LANG]` · a link to the base. Remember PAGE_INDEX.
3. `pages[key=updates]` → remember PAGE_UPDATES. Its body starts with the
   following block. **Keep these keys in English exactly as written, in every
   language** — the update procedure parses them. Put the localized
   explanation, if any, after the block, not inside it.

   ```
   Template: notion-memory-constitution
   Source: <BASE>
   Language: <LANG>
   Installed version: <version from version.json>
   Schema version: <schema_version>
   Constitution version: <constitution_version>
   Installed on: <today's date>
   Last update check: <today's date>
   Update procedure: <BASE>/update.txt
   ```

   Below it, a heading "Update log" (in LANG) and a table
   Date · From · To · What changed · What was not applied and why,
   with a first row recording the installation.

   The `Source:` line is where every future update will be fetched from, so
   whoever controls that address controls the agent's standing instruction
   from then on. Write BASE into it exactly, and treat the line afterwards as
   a field the owner filled in: the update procedure cross-checks against it
   and never rewrites it.

## Step 10. Back-substitution

With `notion-update-page` and `update_content`, replace the remaining
placeholders in the body of the constitution with real ids:
`[ID:page:index]` → PAGE_INDEX, `[ID:page:owner]` → PAGE_OWNER,
`[ID:page:updates]` → PAGE_UPDATES, `[ID:page:history]` → PAGE_HISTORY,
`[ID:page:constitution]` → PAGE_CONSTITUTION.

## Step 11. Starting permissions

Create eight rows in the ⚖️ Permissions base from `seed.permissions` in
schema.json, taking each row's `LANG` branch. The keys of a row map to the
columns of that base through `seed.permissions_columns`: look the localized
column name up there, do not translate the keys yourself.

This is a deliberately cautious starting setup. Only the user raises levels
from here. The last row exists to protect the update chain: the source address
is fixed at installation and only the owner may change it, by hand.

## Step 12. The first day

Create a card for today in the 🗓️ Journal base: the title field = YYYY-MM-DD,
the date field = today, the type field = the "day" option in LANG. The first
facts will attach to it.

## Step 13. Report and bootloader

Show the user, in LANG:

1. One summary line: how many bases were created, how many relations, what
   failed.
2. Links to the knowledge base hub and to the constitution.
3. The ready bootloader text — as a block that can be copied whole. Take it
   from the end of the constitution (the bootloader section) with
   PAGE_CONSTITUTION already substituted.
4. One line on where to paste it: into the agent's settings — the field that
   holds its standing instruction (in Claude, personal preferences or the
   project instructions).
5. An offer to set up auto-updates — the procedure is at BASE/update.txt, and
   how to schedule it is described on the template's Updates page.

The installation ends here. Do nothing further without being asked.
